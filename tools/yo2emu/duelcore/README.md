# duelcore: rules engine (ocgcore) for the YO2 duel server

Duels in YO2 are server-authoritative: the client only executes the `0x6202` commands it is sent. That is why `run.py`
needs a real rules engine. duelcore is a **separate Node process** that runs ocgcore (ocgcore-wasm 0.1.2, Master
Rule 5 by default) and speaks **line-delimited JSON** over stdin/stdout. Python drives it through the `DuelCore` class
(`duelcore.py`).

- It reuses, unchanged, `apps/server/src/duel/engine.ts` (`loadEngine`, `Duel.step`), `data.ts` (CardDB/ScriptStore),
  `bot.ts` (the NPC) and `view.ts` (`applyToTrack`: LP, turn and phase).
- The data in `_vendor/` (cards.cdb, CardScripts, strings.conf; AGPL) is read in place. **Nothing is copied into
  `tools/`.**
- Nothing needs to be installed: it uses the system `node` (v24) and the `tsx` from `apps/server/node_modules`.

## Files

| File | What it is |
|---|---|
| `duelcore.mts` | The Node process: adapter over engine/bot/view + protocol |
| `duelcore.py` | `DuelCore` class: starts the process, reader thread, per-duel queues and callback |
| `pruebas_comun.py` | Test decks (40+40 real passcodes) and the simple policy for player 0 |
| `test_duelo.py` | A full duel against the bot with a narrative and a summary (`python test_duelo.py [seed] [first]`) |
| `test_volcado.py` | A duel of about 3 turns that dumps every event into `out/` |
| `test_bucle.py` | Verification loop: N duels with different seeds + reproducibility (`python test_bucle.py [n] [parallel] [rule]`) |
| `test_errores.py` | Errors without dying, RETRY, surrender, query, `auto_chain=false`, `auto` |
| `test_cerebro.py` | Brain mode (`brain`): `view` in the select, hidden information, `respond.player`, `end.retries` |
| `out/` | Generated by `test_volcado.py`. Contains texts from cards.cdb/strings.conf: **do not commit it to a repository** |

## Starting it

```
node --disable-warning=ExperimentalWarning --import file:///C:/.../node_modules/.pnpm/tsx@4.23.15/node_modules/tsx/dist/loader.mjs duelcore.mts
```

`DuelCore()` does this by itself: it resolves the `apps/server/node_modules/tsx` link and uses `cwd=apps/server`.

- It uses `node --import <loader>` rather than `node_modules\.bin\tsx.CMD`. That way it is **a single process**, and
  there is no `cmd.exe` with a child node that is left orphaned when the parent is killed on Windows. If the loader is
  not found, it falls back to `tsx.CMD`.
- When stdin is closed (`dc.close()`), the process destroys its duels and exits.
- stdout carries only the protocol. Node warnings and any `console.log` from the reused modules go to stderr
  (`dc.stderr_tail`).

```python
from duelcore import DuelCore
with DuelCore() as dc:                         # waits for {"ev":"ready"} (about 3.5 s)
    dc.new(7, decks=[{"main": player_deck}, {"main": npc_deck}], first=1, seed=1234)
    evs = dc.wait(7)                           # events up to the next select/end/error
    sel = evs[-1]
    dc.respond(7, {"type": "SELECT_IDLECMD", "action": "TO_EP", "index": None})
```

`DuelCore(on_event=f)` calls `f(ev)` from the reader thread with **every** event. In addition, each event with an `id`
goes to its duel's queue (`wait`/`next_event`) and the rest go to a global queue (`ping`, `cardinfo`). Several duels can
run at once in the same process: commands are executed serially, and a duel of 30 decisions takes about 30 ms.

## Protocol

One JSON line per command. Every command accepts `"req"`: it is copied into every event caused by that command.

### Commands

| Command | Fields | Effect |
|---|---|---|
| `new` | `id` (any JSON), `decks: [{main:[passcodes], extra:[...]}, {...}]`, `first` 0/1 (default 0), `seed` number/string (default random, returned in `created`), `lp` (8000), `bot` ([false,true]), `brain` (none; `"python"` = player 1, or `[p0, p1]`), `auto_chain` (true), `shuffle` (true), `rule` ("MR5"; also "MR1".."MR4", "GOAT", "SPEED", "RUSH") | Creates the duel, advances the core and emits `created`, messages and the first `select` of the human player (or `end`) |
| `respond` | `id`, `response` (see below), `player` (optional) | Answers the pending decision (of player 0, or of whoever is not a bot). With `player`, duelcore checks that the decision belongs to that player; if not, `error` and the duel keeps waiting |
| `auto` | `id`, `player` (optional) | bot.ts decides for the waiting player (e.g. when that player's time runs out in the client) |
| `surrender` | `id`, `player` (default 0) | `end` with `winner = 1 - player` and `reason: "surrender"` |
| `end` | `id` | Destroys the duel: `end` with `winner: null` and `reason: "ended"` |
| `query` | `id` | `state` event with the full board |
| `cardinfo` | `codes: [...]` | `cardinfo` event with the cards.cdb data (atk, def, level, type, name...) |
| `list` / `ping` | — | Open ids / `{"ev":"pong","duels":N}` |

### Players

- **In the protocol, player 0 is always the human and player 1 the NPC**, whoever goes first. In ocgcore, the core's
  player 0 always goes first. With `first: 1`, duelcore loads the decks the other way round and translates in both
  directions:
  - outgoing: `player`, `controller`, `triggering_controller`, the `players`/`results` arrays and the
    `FIELD_DISABLED` mask;
  - incoming: the `player` of `places`.
- Verified: with `first: 1`, the first `NEW_TURN` belongs to player 1 and no responses are rejected.
- `bot: [false, true]` is the normal case. With `[false, false]`, both players receive `select` (the `player` field
  says whose it is). With `[true, true]`, the duel plays itself.

### Brain mode (`brain`): the NPC is decided by Python

- `brain: "python"` (or `true`) = player 1; `brain: [p0, p1]` = those set to `true`. That player is **not played by
  bot.ts** even if `bot` says otherwise: duelcore emits its `select` like the human's and waits for `respond`.
- Each `select` of a brain player also carries **`view`**, the board as that player sees it (honest information):
  - `view.me` = the player; `view.players[0/1]` (protocol indices) with `deck_count`, `hand_count`, `hand` (codes;
    **empty for the opponent**), `mzone` (7), `szone` (8), `grave`, `removed`, `extra` (own only), `extra_count`;
  - each card on the field: `{code, position, level, attack, defense, owner}`; `owner` in protocol indices (a monster
    taken with Change of Heart has `owner` = the opponent);
  - the **opponent's face-down cards** appear as `{code: 0, position}` (no ATK/DEF).
- The `msg` events still carry full information: the brain must rely only on `view` and on the public messages (which
  is what `research/ia/brain.py` does).
- Empty chain windows are also passed automatically for the brain (`auto_chain`).
- `created` returns `brain: [b0, b1]` and the effective `bot` values. `end` carries `retries: [r0, r1]` (rejected
  responses per player; `human_retries` is still the total).
- Combinations tested (`test_cerebro.py` and the AI tests): `brain: "python"` (human against brain),
  `bot: [true, false]` + `brain: [false, true]` (bot.ts against brain) and `brain: [true, true]` (brain against brain).
- Python client: `dc.new(..., brain="python")`, `dc.respond(id, resp, player=1)`.

### Events

| `ev` | When | Fields |
|---|---|---|
| `ready` | At startup (once) | `cards`, `load_ms`, `pid` |
| `created` | After `new` | `id`, `first`, `seed` (string), `lp`, `bot`, `auto_chain`, `rule` |
| `msg` | Each core message, in order | `type` (name), `type_id`, the message fields |
| `select` | The core is waiting for the human player (or a brain) | The message fields + `retry`, `turn`, `turn_player`, `phase`, `lp` [P0,P1], `ms` (processing time of the command); if the player is a brain, also `view` |
| `end` | End of the duel (WIN, surrender, end or error) | `winner` (0/1/2 = draw/null), `reason` (WIN number or "surrender"/"ended"/"error"), `turns`, `lp`, `decisions`, `human_retries`, `retries` [P0,P1], `auto_passed`, `core_errors`, `ms` |
| `state` | After `query` | `turn`, `turn_player`, `phase`, `lp`, `waiting`, `players[2]` with `deck_count`, `hand`, `mzone`(7), `szone`(8), `grave`, `removed`, `extra`. Each card: `{code, position, level, attack, defense}` or `null` |
| `error` | Any failure | `id`, `cmd`, `error`. The process **does not die**. If the failure is in the format of the response, the duel keeps waiting for the same decision. If the core breaks mid-duel, an `end` with `reason: "error"` is also emitted |

### Event details

- `bigint` → number (every `description` fits in 53 bits).
- Every object with `description` ≠ 0 also carries `desc_text`: the text of the option or effect, taken from cards.cdb
  (strN) or strings.conf.
- `SELECT_OPTION` carries `options_text`. `HINT` messages of type 2, 3 and 5 carry `hint_text`.
- **Hidden information**: the events carry **full information**. The NPC's `DRAW` includes its `code`s, and so do
  `MOVE` and `SET` of face-down cards. It is `run.py` that decides what the client sees (masking with 0, as `view.ts`
  does).
- **`auto_chain`** (true by default): the human's **empty** chain windows (`SELECT_CHAIN` with no options and not
  forced) are passed automatically. They come up in every phase of the opponent: about 90 per duel. Those with
  chainable cards do come out as `select`. `end` says how many were passed (`auto_passed`).
- Determinism: same `seed` + same responses = same duel. This covers the core seed (xoshiro from splitmix64), the
  shuffle and the bot's `Math.random`, all derived from `seed`. `test_bucle.py` checks it.

### Constants

| Name | Values |
|---|---|
| `location` | 1 deck · 2 hand · 4 monster zone · 8 S/T zone · 16 graveyard · 32 banished · 64 extra · 128 material (overlay) · 256 field · 512 pendulum |
| `position` | 1 face-up ATK · 2 face-down ATK · 4 face-up DEF · 8 face-down DEF (in the hand/deck it shows as 10) |
| `phase` | 1 draw · 2 standby · 4 M1 · 8 battle start · 16 battle step · 32 damage step · 64 damage calculation · 128 battle end · 256 M2 · 512 End Phase |
| `WIN.reason` | 1 = LP at 0 (the only one seen in the tests); the rest are ocgcore/EDOPro codes (e.g. 2 = no cards left to draw) |

## Decisions (`select`) and their responses

`response.type` accepts the **name** or the number of `OcgResponseType`. `action` accepts a name or a number. Indices
point into the lists of the `select`.

| `select.type` | Useful fields | `response` |
|---|---|---|
| `SELECT_IDLECMD` (M1/M2) | `summons`, `special_summons`, `pos_changes`, `monster_sets`, `spell_sets`, `activates` (each `{code, controller, location, sequence}`; `activates` also carries `description`/`desc_text`), `to_bp`, `to_ep`, `shuffle` | `{"type":"SELECT_IDLECMD","action":A,"index":i}`. `A`: `SELECT_SUMMON` 0, `SELECT_SPECIAL_SUMMON` 1, `SELECT_POS_CHANGE` 2, `SELECT_MONSTER_SET` 3, `SELECT_SPELL_SET` 4, `SELECT_ACTIVATE` 5, `TO_BP` 6, `TO_EP` 7, `SHUFFLE` 8 (with the last three, `index: null`) |
| `SELECT_BATTLECMD` | `attacks` (`{code,controller,location,sequence,can_direct}`), `chains`, `to_m2`, `to_ep` | `{"type":"SELECT_BATTLECMD","action":A,"index":i}`. `A`: `SELECT_CHAIN` 0, `SELECT_BATTLE` 1 (= attack with `attacks[i]`), `TO_M2` 2, `TO_EP` 3 |
| `SELECT_CHAIN` | `selects` (chainable cards + `desc_text`), `forced`, `spe_count`, `hint_timing` | `{"type":"SELECT_CHAIN","index":i}` or `index: null` = do not chain |
| `SELECT_CARD` | `selects` (`{code,controller,location,sequence,position}`), `min`, `max`, `can_cancel` | `{"type":"SELECT_CARD","indicies":[i,...]}` (sic: `indicies`); `null` = cancel if `can_cancel` |
| `SELECT_TRIBUTE` | `selects` (+`release_param`), `min`, `max` | `{"type":"SELECT_TRIBUTE","indicies":[...]}` |
| `SELECT_UNSELECT_CARD` | `select_cards`, `unselect_cards`, `can_finish`, `min`, `max` | `{"type":"SELECT_UNSELECT_CARD","index":i}`. `i` < len(select_cards) selects; otherwise it unselects `unselect_cards[i-len]`; `null` = finish |
| `SELECT_PLACE` / `SELECT_DISFIELD` | `count`, `field_mask` | `{"type":"SELECT_PLACE","places":[{"player":0,"location":4,"sequence":2}]}` |
| `SELECT_POSITION` | `code`, `positions` (mask) | `{"type":"SELECT_POSITION","position":1}` (one bit of the mask) |
| `SELECT_EFFECTYN` / `SELECT_YESNO` | `code`…, `description`/`desc_text` | `{"type":"SELECT_EFFECTYN","yes":true}` / `{"type":"SELECT_YESNO","yes":false}` |
| `SELECT_OPTION` | `options`, `options_text` | `{"type":"SELECT_OPTION","index":i}` |
| `SELECT_SUM` | `selects_must`, `selects` (`amount`), `amount`, `min`, `max` | `{"type":"SELECT_SUM","indicies":[...]}` (the indices of `selects_must` come first; those of `selects` are offset by len(selects_must)) |
| `SELECT_COUNTER` | `cards` (`count`), `count` | `{"type":"SELECT_COUNTER","counters":[n per card]}` |
| `SORT_CARD` / `SORT_CHAIN` | `cards` | `{"type":"SORT_CARD","order":null}` (default order) |
| `ANNOUNCE_RACE` / `ANNOUNCE_ATTRIB` / `ANNOUNCE_CARD` / `ANNOUNCE_NUMBER` | `available`, `count` / `opcodes` / `options` | `{"races":[...]}` / `{"attributes":[...]}` / `{"card":code}` / `{"value":i}` |
| `ROCK_PAPER_SCISSORS` | — | `{"type":"ROCK_PAPER_SCISSORS","value":1\|2\|3}` |

**`field_mask` of SELECT_PLACE/DISFIELD**:
- it marks the zones that are **not** available;
- it is relative to the player choosing: bits 0-7 = their monsters, 8-15 = their S/T, 16-31 = the same for the
  opponent;
- `places[].player` uses protocol indices (0 = human).

Example: `field_mask 4294967264` = `0xFFFFFFE0` → monster zones 0-4 free. `free_places()` in `pruebas_comun.py`
resolves it.

If the response is wrong:
- **wrong type or format** (e.g. `SELECT_CHAIN` for a `SELECT_IDLECMD`) → `error` and the duel keeps waiting;
- **valid format but illegal** (e.g. `index: 99`) → the core answers RETRY and duelcore emits the same `select` again
  with `retry: true`.

## Limitations

- **bot.ts is simple**:
  - it summons its best monster, plays spells from the hand, sets traps and attacks with everything, even against a
    stronger monster;
  - it is capped at 10 actions per turn;
  - for an NPC with a personality: `brain` mode + `research/ia/brain.py`.
- **Rules**: MR5 by default, like the engine in `apps/server`. YO2 (2008) belongs to the Master Rule 1 era: try `rule: "MR1"`. With decks
  of normal monsters and simple spells, both give the same result.
- **Full information** in the events: `run.py` must mask the NPC's hand and face-down cards.
- **duelcore has no translator to 0x6202**: mapping these messages and decisions to the client's commands is done
  outside it (see `research/lockstep/NOTES.md` and `research/traductor/NOTES.md`). duelcore only provides the rules.
- `Duel` has a `private` constructor in TypeScript. The adapter uses it anyway (the restriction does not exist at run
  time) to set its own seed and order without touching engine.ts. If engine.ts changes the constructor signature,
  `createDuel()` in `duelcore.mts` must be updated.
- `query()` in Python reads from the duel's queue: call it only while the duel is stopped at a `select`, not at the
  same time as `wait()` in another thread.
- **`SELECT_SUM` is broken in ocgcore-wasm 0.1.2** (seen with the NPC decks): the parser reads `selects` before
  `selects_must` (the EDOPro core writes the mandatory ones first), and each card without the u32 `position` that the
  EDOPro `loc_info` carries. The result is a garbage list (e.g. `{"code": 8, "controller": 26, "location": 43}`) and
  **no response is valid**: a ritual (Advanced Ritual Art, Curse of the Masked Beast...) leaves the duel asking for
  the same thing forever. bot.ts ends in `error` ("el bot no da una respuesta válida a SELECT_SUM"). The brain in
  `research/ia` does not activate rituals; if the human does, `run.py` should end the duel. The real fix is a patch to
  the library's parser (not done).
- bot.ts can loop in a chain window (it activates a repeatable effect from the graveyard over and over in its End
  Phase; its 10-action cap only applies to the main phase). duelcore cuts it off after 5000 consecutive decisions
  ("el bot no termina"), but if the other player gets a chain window on every round, the loop does not stop by itself:
  whoever runs the duel must set a decision cap.
- Cards without a script or with unusual effects depend on CardScripts. Core warnings come out in `end.core_errors`; in
  the tests it was always empty.
